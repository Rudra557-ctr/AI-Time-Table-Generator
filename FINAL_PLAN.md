## Executive Summary — the honest verdict

The **engineering is genuinely ahead of the product.** The CP-SAT solver core is solid, well-tested, and well-documented — better than most hackathon projects at this stage. The gap is that a full data-entry wizard got built (16 steps, 587-line schema, 3-tier validator) **before anyone outside the builder ever touched it**, and there is currently **no confirmed college, department, or person** who has agreed to use this. That's the one finding this whole plan is built around: stop building for a hypothetical admin and go get a real one, fast, with the least new code possible.

Nothing here says "start over." The solver is the hard part and it's done. This plan is about sequencing the next few weeks so the next thing you build is validated by a real stranger's confusion, not by more assumptions.

## 1. What's Already Done — and what's genuinely good

Don't undersell this. This is a lot of real, working engineering:

- **CP-SAT solver core is solid.** `sih_solver/hard.py`, `full_model.py`, `soft.py` implement 10+ hard constraints (faculty/room/section/student collisions, synchronized electives, equipment-type matching, workload caps, fixed events) and 9 weighted soft constraints (student gaps, consecutive load, spread, faculty gaps, building movement, preference, balance, wastage). Hard model solves **OPTIMAL in ~107s**; hard+soft (hinted) reaches **FEASIBLE in ~122s** on a 133-offering, 370-session, 16-section dataset. This is the hardest technical risk in the whole project and it's de-risked.
- **101 tests, not a token test file.** 45 tests on the solver core (collisions, preprocessing, batching, soft scoring), 56 on the new data layer (schema validation, cross-dataset FK/solvability checks, API CRUD) — all currently passing, the fast 84 of them in under 8 seconds combined.
- **The adapter's fuzzy column mapping (`sih_solver/adapter.py:159`, `infer_column_mapping`) is a real asset.** It already tolerates messy, differently-named CSV headers. This is more valuable than it looks — see §3.
- **The schema/validator layer is good engineering, not scope creep.** `sih_solver/schema.py` (19 datasets, typed field specs) + `sih_solver/validator.py` (L1 schema / L2 referential / L3 solvability) turns "solver silently fails or runs 150s to say UNKNOWN" into structured, specific, fixable error messages *before* a slow solve is wasted. The idea is right. It's just ahead of any evidence that the *wizard UI* built on top of it is the right way to surface it (see Weak Point #2).
- **Lab-batch splitting works.** 16 oversized lab offerings auto-split into 32 batches, solves OPTIMAL in 45s — a real, non-obvious feature (`sih_solver/batches.py`).
- **Documentation discipline is unusually good.** `PLAN.md` and `CONSTRAINTS.md` carry file:line references for nearly every constraint and function. Most projects at this stage have none of this. Keep doing this — it's why this plan could get written accurately in one sitting instead of needing to reverse-engineer the codebase.

## 3. The Bet This Plan Makes

**Chosen approach (A): get a real test fast, with the least new infrastructure possible.**

Two other approaches were considered and explicitly rejected for now:
- **"Harden into a real multi-tenant product first"** (auth, Docker, CI, solver perf, *then* find users) — rejected because it repeats weak point #1 at a bigger scale: months of infra investment on top of unconfirmed demand is the classic build-before-validate trap.
- **"Position as an open-source scheduling engine instead of a college product"** — a legitimate fallback if Phase 2 below turns up no real interest, but premature to commit to now; it gives up on the product path before actually testing it.

**The core idea:** the fuzzy CSV adapter you already built (`adapter.py:infer_column_mapping`) is the real wedge — colleges already have this data somewhere messy. Lead with "upload what you've got," let the validator show exactly what's missing, and only use the wizard's per-dataset editors to patch specific gaps — not to re-enter everything from a blank form. Time how long it takes a real stranger to go from zero to a generated timetable. That number is the actual demand test, more informative than asking anyone if they "like" the wizard.

### Phase 1 — Flip the wizard to upload-first (the core of Approach A)

- [x] Made the wizard's landing screen upload-first: a fresh/empty job now shows "Upload your existing data" (reusing the already-working `/api/upload` bulk import) as the primary action, with "Start from blank forms" as a secondary fallback — not a forced "step 1 of 16." (`frontend/js/app.js`: `renderStart`, `renderUploadWidget`, `boot()`.)
- [x] After upload, the wizard now auto-routes to the first step with an actual BLOCKER (`routeToFirstGap()`), or straight to Review & Solve if there are none — instead of dropping the user wherever they happened to be.
- [x] **Checked the "required datasets" claim and it was wrong.** Tested empirically: filling only the 7 datasets in `required_datasets()` left `can_solve=False` — `sections.program_id`, `courses.department_id`, and `faculty.department_id` are FK fields that always need `programs`/`departments` populated too, but those were miscategorized as "optional." Fixed `sih_solver/schema.py:required_datasets()`/`optional_datasets()` to the real, verified 9-dataset minimal set (added `departments`, `programs`) and updated the two tests that hardcoded the old wrong list (`test_schema.py`, `test_data_api.py`). Re-verified empirically after the fix: the corrected 9-dataset set reaches `can_solve=True` with 0 blockers.
- [x] Added a visible progress indicator during solve: a persistent "this can take up to 2 minutes, keep this tab open" notice plus a live elapsed-seconds counter, separate from the polled status line so it doesn't get wiped every 2s poll tick.

**Two real, previously-latent bugs found by actually driving the upload-first flow end-to-end (not by inspection) — both fixed and verified:**

1. **`backend/app.py`'s "strip the demo filler" logic matched dataset names by substring** (`if ds in w`). `"faculty"` is a substring of `"faculty_availability"`, so uploading `faculty.csv` alone (without also uploading the optional `faculty_availability.csv`, which gets auto-filled from the demo dataset and then is supposed to be stripped back out) caused the strip logic to match `"faculty"` first and **delete the user's real, correctly-uploaded faculty.csv instead of the actual filler file**. Reproduced: uploading 9 real files left `faculty` with 0 rows. Fixed with an exact regex match (`Missing (\w+)\.csv`) instead of substring search. Re-verified: same upload now correctly shows `faculty: 40 rows`, `can_solve: True`.
2. **`backend/app.py`'s solve endpoint passed `str(normalized_dir)` into `build_full_hard_model`, but `sih_solver/preprocessing.load_all` did `root / fname` assuming `root` was already a `pathlib.Path`** — `str / str` raises `TypeError`. This meant `POST /api/solve/{id}` had never actually worked end-to-end through the wizard path before this test. Fixed `load_all` to coerce `root` to `pathlib.Path` defensively. Re-verified: solve now runs to completion (reaches `UNKNOWN`/`FEASIBLE` at the time limit like the documented CLI path does, instead of crashing instantly).

Both bugs were invisible to the 84 existing unit tests (none of them exercise `/api/upload` → `/api/solve` back-to-back with a realistic multi-file upload) — direct evidence for why Phase 2's "watch a real person use it" matters more than more unit tests would have here.

## 8. Plan Update (2026-08-23) — After Finding the Real Problem Statement

Everything above was written and executed (Phase 0 + Phase 1 done) before we had the actual SIH problem statement in hand. It named a specific school — **USAR (University School of Automation & Robotics), GGSIPU, Dwarka + East Delhi campuses** — dealing with NEP 2020: four B.Tech programmes sharing a limited pool of classrooms/labs/faculty, cross-programme PCE/OAE electives, lab batches that must be split (and possibly rotated), guest/visiting faculty available only on fixed days, and cascading changes when one section moves. The "Expected Solution" also explicitly names required platform capabilities: automated generation, conflict detection, **modification suggestions**, and **dynamic timetable updates**.

Good news first: this isn't a pivot. The hardest-to-build part of the spec — cross-programme electives, lab batching, room/equipment matching, guest-faculty fixed-day availability — is exactly what `hard.py`/`preprocessing.py` already model, in unusual detail for a hackathon build. This update sharpens the target and closes two real gaps, it doesn't invalidate anything already built.

### Remove / stop / deprioritize

1. **Stop targeting "any random college" for Phase 2.** The plan's own §6 already flagged "no one lined up yet" as the top risk — that's now a much narrower, more solvable problem. Retarget outreach specifically at USAR, GGSIPU, or an equivalent NEP-2020 multidisciplinary program. A generic college contact is now a worse test than a targeted one, because the hard constraints already built are tuned to *this* structure specifically.
2. **Do not build the AI-assisted importer or a grid-timetable-specific importer yet**, despite the data-format conversation earlier in this session. Both are still bets on an unconfirmed data shape — the new problem statement doesn't resolve that uncertainty, it just tells you *who* to ask. Keep them parked until Phase 2 evidence says otherwise.
3. **Stop investing further UI polish in the 16-step blank-forms wizard** (electives/events/advanced tabs, matrix editors). It's already demoted to a secondary path since Phase 1. No further work there until real usage says it's the bottleneck.
4. **Retire `PLAN.md`'s §7 "Clarifying Questions" items 1–2 as answered** — "priority: solver stability vs. product demo" and "should lab batches be user-configurable" are effectively resolved by the real spec: lab batching is a named, required capability, not an optional toggle.

### Add — prioritized, cheapest/most-confirmed first

1. **[Do now — small, zero uncertainty]** Fix the silent-dropped-column import gap from earlier in this session: when `adapter.py`'s column auto-mapping can't confidently place a header, surface it for the user to manually assign or skip instead of silently dropping that data. This was already scoped as "the optimal move" two turns ago and is still correct — it's not a bet on data shape, it's closing a real silent-failure hole. **Not yet built.**
2. **[Do next — the sharper Phase 2]** Retarget outreach: reach out to anyone connected to USAR/GGSIPU, or failing that any NEP-2020 multidisciplinary program with cross-programme electives. Script the demo around the exact language of the problem statement (PCE/OAE, lab batch splitting, guest-faculty fixed days) — it's the strongest possible pitch because those are the literal constraints already coded.
3. **[Real gap #1 — "modification suggestions"]** Wire the existing but unused `soft.py:apply_human_feedback` into an actual UI action: a user flags a problem on a specific section/day, weights adjust, the system re-solves and presents the change as a labeled alternative — not a silent overwrite. Medium effort; the mechanism already exists, it just isn't reachable from anywhere.
4. **[Real gap #2 — "dynamic timetable updates," the one that matters most]** Build incremental re-solve: when one input changes (a faculty member becomes unavailable, a room is pulled, a section is added), warm-start the solver with `AddHint` fixing every unaffected assignment, re-solve, and show only the diff. This is the direct technical answer to the problem statement's own framing — "every change to one section cascades through the rest" — and it's explicitly named as a required capability, not a nice-to-have. This is very likely the single highest-leverage piece of *new* engineering in this entire plan, higher priority than solver-performance tuning (§4 Phase 3 "deferred" list) — it's a named requirement, not an optimization.
5. **[Resolve, don't guess]** Get a direct answer on whether "lab batches must be split and rotated" means a multi-week alternating cycle (not modeled — the solver is single-week only) or just the parallel split already built in `batches.py`. This is a modeling question a real USAR contact can answer in one sentence; don't build either interpretation speculatively.
6. **[Low priority, doc hygiene]** Once the above lands or Phase 2 happens, update `PLAN.md`/`CONSTRAINTS.md`/`README.md` to name USAR/GGSIPU/NEP 2020 explicitly instead of generic "college timetable" language, so the next session doesn't have to rediscover this from a pasted paragraph.
